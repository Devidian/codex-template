# Contributing

Start from `main` on a `feature/`, `fix/`, `chore/`, or `docs/` branch. Continue on an existing development branch instead of nesting branches. Use Conventional Commit titles for commits and PRs. Keep changes scoped and update docs and `CHANGELOG.md` under `Unreleased` when behavior changes.

Run relevant checks while developing. Before requesting acceptance, complete the checks in [testing](docs/development/testing.md), address review findings, and summarize scope, architecture, tests, changed-line and overall coverage, limitations, and risks in the PR. A human must explicitly accept before squash merging. Releases follow [releasing](docs/development/releasing.md).
